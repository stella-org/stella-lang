# Design Decisions

Each decision states what Stella does, why, and how costly it is to revisit. Alternatives that Stella rejects are recorded with the reason, so that reopening a decision starts from the argument rather than from scratch.

Reversibility is graded **low** (the decision is load-bearing; changing it propagates widely), **medium**, or **high** (local, or surface-only).

## Calculus and kinds

| # | Decision | Rationale | Reversibility |
| --- | --- | --- | --- |
| D1 | The Core calculus is **System F extended with kinds, higher-kinded type variables, rows, and effect rows**. It has no type-level lambda, so it is a subsystem of System Fω rather than Fω itself. It does not adopt System FC coercions | Without type-level functions, type equality is syntactic apart from row normalization. Type constructors can be abstracted over (`forall (f : Type -> Type)`) but anonymous type constructors cannot be defined. This is the level of Haskell 98 and PureScript | Adding type-level functions moves the calculus to Fω. The same judgement as D6 |
| D2 | **Kinds and types are separate syntactic classes.** Stella does not follow PureScript 0.14+ in unifying them | With no type-level functions the unification buys little, and separation avoids `Type : Type`. Kind checking terminates trivially and independently | Medium. The reflection API carries both a `Kind` and a `Type` |
| D3 | Kind polymorphism is **prenex only**. Kind schemes appear only on declarations — type constructors, data constructors, and top-level values. Neither types nor terms have kind quantifiers; instantiation is written explicitly at the use site as `T [[κ̄]]` or `M.x [[κ̄]]` | Preserves decidability while retaining higher-kinded types and the generality of `Row ε`. `Proxy : forall k. k -> Type` is prenex and therefore expressible. Rank-2 kinds such as `(forall k. k -> Type) -> Type`, and kind-polymorphic functions, are not | High |
| D24 | **Kinds are stratified into three layers**: row element kinds `ε ::= Type \| Effect`, general kinds `κ` (where `Row` takes only `ε`), and quantifiable kinds `q` (which exclude `Effect`). Every site that introduces a type variable, and every `[[κ̄]]`, requires `Γ ⊢ κ qkind`, and an arrow is quantifiable — and a type constructor declarable — only where it produces `Type` | Without the restriction, degenerate row kinds such as `Row (Type -> Type)`, which can have no elements, become well-formed, and `forall (e : Effect)` becomes derivable. `Effect` is needed as the result kind of effect constructors but must not be quantified. Higher-kinded types (`forall (f : Type -> Type)`) are unaffected. Confining row kinds to argument position is what keeps `nf` total on well-kinded rows: a type of kind `Row ε` is row syntax and nothing else | Low. Permitting quantification over `Effect` is also coherent, but then D16's restriction must be imposed separately |

## Rows

| # | Decision | Rationale | Reversibility |
| --- | --- | --- | --- |
| D4 | Rows are **sharp**: no key occurs twice. Stella does not adopt Leijen's scoped labels | Duplicate keys make `⊎` non-commutative and give the position of known fields relative to an unknown tail semantic weight, so no normal form exists without closing row variables. With sharp rows the normal form is a finite map from keys to payloads plus a set of row variables, and equality is fully decidable | Low. It propagates through the entire row theory |
| D16 | **Every row element has a key, and the key is one of five constructors**: `SymbolKey` for a written field or instance name, `TagKey` for a structural variant constructor, `PositionKey` for a tuple component, `EffectKey` for a declared effect, `RegionKey` for a handler's region of cells (D36). An effect element derives its key from the effect at the head of its payload unless a `SymbolKey` is written for it | Whether a key is written is not a concern of row theory, so one theory serves records, tuples, variants, effects, and regions alike. What every key must be is **rigid** — independent of metavariable solving — for row equality to be decidable, which is what rules out using a payload type as the key. Deriving an effect's key keeps the common case free of ceremony; writing one is what lets a single effect appear twice in a row, which sharpness would otherwise forbid. `PositionKey` and `RegionKey` are the two no source syntax writes: elaborating a tuple derives the first from where a component stands, and only a handler's `cells` produces the second, which is what keeps a region from being discharged by anything but the `handle` that owns it | Low |
| D5 | Structural relationships between rows are expressed by **erased constraints in the Core context**, `k ∉ ρ` and `ρ1 # ρ2`. They are not dictionaries | The row solver and the type class resolver are separate mechanisms. `#` carries no run-time content | Low |
| D6 | Core has exactly three row operators: `()`, `( ent \| ρ )`, and `ρ1 ⊎ ρ2`. **`Difference` and `Map` are not in Core** | Term-level `restrict` covers what `Difference` is needed for. `Map` requires type-level functions, whose termination is unsettled. Both can be added later as type-level functions over `Row ε`; admitting them now would make row equality undecidable | Medium |
| D13 | **Every structural key is a literal.** A `SymbolKey` and a `TagKey` are written in the source, and a `PositionKey` is what elaborating a tuple derives from where a component stands; none is a variable, and the kind grammar has no `Symbol` kind | This is not merely a simplification: it keeps row keys rigid, which is what makes row equality decidable, the same requirement as D16. The role a `Symbol` kind plays in PureScript — reflecting type-level labels to run-time strings — is served by `normalizeRow` in the elaborator. Note that the `Symbol` of `SymbolKey` is the written name itself, not a kind | Low. Introducing a `Symbol` kind requires re-validating row normalization and keeping key variables out of Core's row-extension position |

## Effects

| # | Decision | Rationale | Reversibility |
| --- | --- | --- | --- |
| D7 | Function types **carry an effect row**: `τ1 -{ρ}-> τ2`. Stella does not use an `Eff` monad | Making effects a type constructor splits function types into pure and effectful, and that split then appears at every FFI boundary and in every treatment of exceptions and asynchrony. Putting the row on the arrow makes purity the case where `ρ = ()` | Low |
| D8 | Effect containment is **not subtyping**. Widening is written explicitly as `openEff` | Core type checking then requires only syntactic equality. A secondary benefit is diagnostic precision: because rows do not widen silently, an unsatisfied obligation is reported at the function that failed to declare the effect | High. A decidable subsumption judgement on effect rows is available as a fallback |
| D15 | Handlers are **deep**: after a resumption, control is under the same handler | Standard. A resumption runs the rest of the handled computation under the handler that captured it, so every later operation of the same key reaches that handler again without the clause reinstalling it, and a handler's meaning is fixed by the handler alone rather than by what each of its clauses does. Shallow handlers can be built from deep ones. How a backend reinstalls the handler is its own; the machine re-pushes the captured segment with the marker at its bottom ([Bytecode](../05-Backend/01-Bytecode.md)). The number of resumptions is a separate decision, D18 | High |
| D18 | Core **does not restrict how many times a delimited continuation may be resumed**. The reference semantics is multi-shot. The v0.1 JavaScript and Wasm backends do not satisfy this: a second resumption raises a dedicated run-time error. This is an accepted, documented soundness gap that v1.0 must close | Continuations are ordinary function values, so multi-shot requires nothing extra; restricting it would require affine types in Core. The cost is backend-specific: one-shot is natural on JavaScript generators and on Wasm stack switching, while a native backend has no reason not to implement multi-shot | Medium. The Core decision is stable, but the v0.1 backends are non-conforming implementations |
| D28 | A handler clause is either **`full`**, which binds the continuation, or **`fast`**, which does not. A `fast` clause names only the operation's arguments; its body has the type the continuation resumes with, and reduction evaluates that body once and returns the value it produces to the point of the `perform`, constructing no continuation. **Core writes the marker on every clause**, there being no default to fall back on | A `fast` clause's body is checked at the resume type and its premise never mentions the answer type, so the clause can neither bypass the evaluation still to come in order to supply what the `handle` returns, nor invoke the handled continuation zero or several times, having none to invoke. Reduction binds the body once, and on each run where it returns a value the original evaluation context continues from that value. Binding it rather than embedding it at the `perform` site is what lets a clause of a handler owning a region stand at a row the handled computation does not ([Semantics](../03-Typed-Core/06-Semantics.md), D36). **This is a property of the clause and not of the program around it**: where the body performs an operation of the residual row whose `full` handler resumes more than once, that handler's continuation runs the rest of the handled computation again. What follows is narrower and is what matters for D18 — implementing a `fast` clause calls for no multi-shot continuation, so the construct that can demand one is `full` alone. The property is declared rather than inferred because it is not visible in a clause's syntax: an occurrence of `k` under a lambda may be applied twice, and two occurrences in separate branches of a `case` may amount to one resumption | Medium. Writing the marker on every clause keeps any clause from being silently reclassified, but the distinction reaches Mid IR and the backends |
| D36 | **A handler may own a region of cells.** A handler writing `cells [r] ( k̄ : σ̄ )` is applied as `handle e with h @ ( ē )`, which opens one cell per key; `readCell k` reaches the innermost region declaring `k` and `writeCell k e` sets it. The region is a row element keyed `RegionKey` (D16), carried by the **operation clauses** and by nothing else — not by the handled computation, and not by the return clause, so an ordinary return hands back no state of its own accord. A handler that declares no region takes the rule it always took. **A cell is a binder with a lifetime, not a location**: it lives in the evaluation context and a write rewrites that context, so a continuation whose captured context contains the region carries the values it was captured with | This is `ST` rather than a state monad, and the two coexist: cells buy tail resumption, while a handler that wants its final state returned for it writes the parameter-passing one instead and pays for the continuation. What the rules guarantee is narrower than "the state cannot escape": a `full` clause stands at the region's row and may copy a cell's value into the answer deliberately. What no clause can do is hold a reference into a region that outlives it, which is the escape condition below; a term that carries the whole `handle` carries the binder too and is closed with respect to the region. Putting a cell in the evaluation context rather than in a store is what makes both halves true — a `fast` clause captures nothing, so the common path copies nothing, and where a capture does happen the values ride along in a segment that was being copied anyway. Which continuations carry a region is decided by where the capturing handler stands: one installed outside the region carries it, and the handler owning the region does not, its cells staying live across its own resumptions ([Semantics](../03-Typed-Core/06-Semantics.md)). The reduction relation stays store-free, and `Ev_c` picks the innermost region exactly as `Ev_k` picks the innermost handler. Core needs no rank-2 quantifier for the scope discipline, `cells` being a binder: the region variable is written there, and `r ∉ ftv(β) ∪ ftv(ρ)` is what stops a free reference into an open region — a closure over a `readCell`, say — reaching the answer type or the residual row. It does not, and need not, stop a continuation an outer handler captured across the whole `handle`: that carries the region binder along with everything under it, mentions no `r`, and is exactly the closed package the snapshot reading rests on. A handler polymorphic in its residual row assumes `RegionKey ∉ ρ`, which is what a sharp `( region r ι | ρ )` needs and what rejects a region opened inside another. A cell is named by a key rather than held as a value, so no handle exists whose type could forget the region | Medium. The row theory is untouched and the reduction relation gains no store, but the form reaches Mid IR and every backend |
| D20 | **`IO` is an ordinary monad, `IO : Type -> Type`, not an effect.** Every effect is interpreted into `()` or `IO`; an effect that is interpreted into neither is never executed. The entry point is `main : IO Unit` | `IO` alone admits no operation signature, so it is not an algebraic effect. As an effect constructor it would also introduce containment between effects — `Console` is a subset of `IO` — which sharp rows keyed by constructor cannot express. Removing it from the effect world dissolves the containment question and closes the question of what happens to uninterpreted effects. An effect whose *operation* takes an `IO` — a lift — subsumes other capabilities functionally, but it does so through an explicit handler and keeps its own key in the row, so no containment between effects arises and it is admitted ([Effects](../03-Typed-Core/03-Effects.md)). Preserving D7's granularity requires the standard library discipline of confining `IO` to interpreters and `main` in ordinary code | Low. It propagates through the standard library and runtime boundary |

## Terms and matching

| # | Decision | Rationale | Reversibility |
| --- | --- | --- | --- |
| D9 | Pattern matching is represented in Core as a **decision tree with join points** | Makes the decision structure explicit and turns lowering to Mid IR join points into a structure-preserving translation | Low |
| D10 | A non-exhaustive match produces the **`Partial` effect**, surfacing partiality in the type. `fail` is derived notation for this, not a Core primitive | Gives the effect of PureScript's `Partial` class without a class mechanism or a dedicated language feature | Medium |
| D11 | **Core has no implicit arguments.** Elaboration turns them into ordinary arguments | After elaboration, a type class is nothing but dictionary passing | Low |
| D12 | **Core has no metavariables.** They exist only in Core⁺ | Keeps the trusted core small | Low |
| D14 | Recursive bindings must be **guarded**: each right-hand side is syntactically a function value | Under strict evaluation this rejects `letrec x = f x` at type-checking time rather than deferring it to an uninitialized reference at run time | High |
| D21 | An **operation signature is not a function type**; it is written `σ ->* τ`. Exactly one `->*` appears, at the same precedence as `->` and right-associative, on the spine. Everything to its left is an argument; what stands to its right is the type the continuation resumes with | In Stella `->` asserts an empty effect row, so using it for an operation — the one thing that is by definition not pure — says the opposite of what is meant. The position of `->*` coincides with the arrow that carries the effect row in the generated function type, so currying and the purity of partial application follow from the existing rules. Multi-argument operations are expressible while Core operations remain single-argument | High. Surface syntax only |
| D35 | **An application evaluates its argument before its function.** A spine is therefore evaluated right to left and applied left to right: `f x y z` evaluates `z`, `y`, `x`, `f`, and then applies. This is observable — the order of two `perform`s in argument position, and which of a fault, a divergence, and the callee's own effects happens first — and it is the language's order rather than one backend's ([Semantics](../03-Typed-Core/06-Semantics.md)) | With the function evaluated first, the evaluation of `f x` stands between the arguments of `f x y`, so an effect it performs falls between them and a spine cannot be collected into one multi-argument call without reordering. Argument-first removes that: every argument reaches a value before any application happens, and a call carrying the whole spine performs exactly what the nested applications did (D30). Making the arguments thunks, or adding an n-ary application to Core, would buy the same thing at a higher price — the first changes what a program evaluates and the second enlarges the trusted core. Multi-argument operations and syntax macros expand into curried application and take the same order, there being no second rule for them | Medium. It is observable, so it cannot change once programs depend on it, but it touches no typing rule, no AST, and no part of the type checker |

## Modules, FFI, and surface syntax

| # | Decision | Rationale | Reversibility |
| --- | --- | --- | --- |
| D29 | **A handler is a declaration form that desugars to an ordinary function**, and `implicit` marks one the elaborator may supply where the author wrote none. Insertion happens only at a checking position, and only where the **complete plan — the handlers and the order they nest in — is unique**; several valid orders are an ambiguity error. Core gains nothing: what elaboration produces is application, `openEff`, and `handle` ([Effect Handlers](../02-Surface-Language/02-Effect-Handlers.md)) | Effect adaptation is a term transformation of the surface rather than subsumption in the type system, so D8 survives intact and an inserted handler is checked like a written one. Requiring the plan to be unique rather than assuming that independent handlers commute is what keeps the meaning determined: a `fast` clause performs an operation of the residual row, and what becomes of the computation then belongs to whichever handler is installed there (D28), which no declaration records. Insertion is driven by the difference between two rows rather than between two types, which is what keeps the search finite and directed — an implicit handler that changed the answer type would make it implicit coercion instead | Medium. The declaration form is surface-only, but which programs are accepted depends on the insertion rule, so relaxing it later is easier than tightening it |
| D17 | Effect sequencing is **direct style**. `perform` is a Core construct and does not appear in surface syntax; operations are written as ordinary function calls and the elaborator emits `perform` | This is D7 seen from the surface. Requiring `do` and `bind` for effects would restore, at the level of syntax, the pure/effectful split that D7 removed from types. Coexistence with classical monads is unaffected, provided `bind` is effect-polymorphic. The spelling of `do` is left to a library syntax macro | Low. It moves with D7 |
| D19 | **Stella uses FFI far more sparingly than PureScript**: leaf operations only, a small versioned ABI surface (D26), no dependence on representation, and per-backend implementations kept separate from declarations | Mid IR is designed not to leak representation to backends, and FFI is the only path around that. In PureScript, FFI code depends on the representation of values, which takes the choice of representation away from alternative backends and forces every library with FFI to be rewritten per backend. A small ABI surface does for backend independence what a small trusted core does for soundness | Low. It shapes the whole standard library |
| D23 | **Every arrow in a runtime-bearing position of a `foreign` type has an empty effect row.** Effects on the outside world are expressed by returning `IO` | `handle` intercepts only `perform`, while a `foreign` application calls the implementation directly. An effectful `foreign` would therefore let a handler remove the effect from the row while the actual effect bypasses the handler's clauses. On the argument side the same rule prevents the lowering's calling convention from leaking across the FFI boundary. It holds of the payload of a row element, which hands a value across as an argument does, and not of a constraint, which is erased and carries none. The condition is syntactically checkable | Low. It is inseparable from D20 |
| D22 | **Modules are namespaces.** Stella has no ML-style module system: no functors, no sealing by signature, no first-class modules. Data abstraction is provided by export lists. Local open `M.( … )` is available, but declaring a dependency and introducing names into scope are separated, so dependencies remain determined by the module header | Core names are fully qualified and module boundaries disappear during name resolution. Functors would require Core to express functor application and signature matching, enlarging the trusted core by an order of magnitude. Header completeness is what makes incremental and parallel builds cheap | Low. Strengthening the module system requires returning to the Core design |
| D25 | **Executing an `IO` lies outside Core.** Core reduction halts at an `IO` value; execution is the responsibility of the runtime ABI, a separate normative specification covering `Base.IO.pure`, `Base.IO.bind`, native leaf actions, world state, and the invocation of `main` ([Semantics](../03-Typed-Core/06-Semantics.md)) | Keeps **world** state out of the trusted core: a file, a clock, and a console are reached by running an `IO` and by nothing else. What Core owes the ABI is narrow: D23 keeps effects out of the arrows of a `foreign` type, and the conformance condition on `δ_f` keeps it from *running* the reified computation it builds, so an `IO` value is inert until executed. What that condition does **not** do is keep every effect out of an implementation — an entry asserting no `#observ(none)` may read and write hidden state, and may fault, when it is applied — so the reduction relation is **guaranteed** closed and deterministic for a program whose every `δ_f` is Core-modelled — a saturated call doing nothing beyond returning an outcome its arguments fix, a premise this relation carries beside `Σ ⊨ G` — and gives an entry that reads or writes hidden state no rule at all, which leaves such a program unshown rather than non-deterministic ([Semantics](../03-Typed-Core/06-Semantics.md), D41). The second half is an obligation on the backend rather than a consequence of D23. The cost is that the ABI must be specified before a program runs end to end | Medium. The boundary is the interface between the language and every backend |
| D41 | **Stella distinguishes three classes of effect — proper, reified, and observational** ([Semantics](../03-Typed-Core/06-Semantics.md)). A `foreign` declaration may assert `#observ(none)`; one carrying no directive is treated conservatively as `MayObserve`. **Faulting is also a sort of observational effect.** An optimizer treats a `MayObserve` call as a **full sequencing barrier** — preserved, neither duplicated nor merged, and keeping its position in the original order — while `None` admits the transformations any pure call admits ([Interface](../05-Backend/03-Interface.md)). **The contract binds whoever implements the entry and is indifferent to whether that is the machine or the host** ([Modules](../06-Modules/01-Modules.md)) | Nothing a foreign does behind its type is inferable from that type, and the two things an optimizer most needs — whether a call may be dropped, and whether two may be shared — are exactly what the type does not say. Defaulting an unannotated entry to the conservative side is what keeps a wrong optimization from being the silent outcome of an omission, and it is what lets the annotation be added entry by entry rather than all at once. Folding faulting into the class follows from the definition rather than from convenience: erasing a call that would have faulted removes the fault, which is the observation the class names, and a finer grading would describe what one implementation happens to do rather than what a declaration promises — the same reason Stella reaches for FFI sparingly (D19). Making the contract indifferent to the implementer is what keeps one declaration from meaning two things: an entry the machine carries out as an operation and one a host supplies are two routes to a single promise, and which route is taken decides only whose defect a violation is. **What this decision does not fix is the operational model.** Being modelled by Core's reduction relation is a **third** notion beside the two above: it asks that returning an outcome the arguments fix, a value or a fault, be the **whole** of what a saturated call does — so no hidden read, no write, and no identity the arguments do not determine. Constraining the outcome alone would not do, since an entry writing through an array it is handed returns `Unit` whatever it wrote. **It is independent of the directive in both directions**: this condition permits a deterministic fault, which the directive forbids, and it forbids an allocation the arguments do not determine, which the directive permits where nothing can observe it — so an unobservable allocation stays available as a pure entry without Core's determinism being loosened for it. It is a premise of the reduction relation beside `Σ ⊨ G` rather than a clause within it, the two binding different parties — conformance is what an implementer owes, and admits `unsafeSet`, while this is what the rules need, and does not — and an unannotated entry may satisfy it — `Base.String.codePointAt` faults and is `MayObserve`, and its outcome is determined all the same. What falls outside is the mutable trio, `Base.Array.unsafeNew`, `unsafeSet`, and `unsafeIndex`, the last for the unrecorded state it reads rather than for the fault it raises: the rule `M.f ς → δ_f(values(ς))` gives such an entry no step, and the four properties are stated over environments where every `δ_f` is Core-modelled. Whether to add an observational store to the configuration or to leave such an entry a trusted boundary is open ([Open Questions](../99-Open-Questions/01-Open-Questions.md)) | Medium. Weakening the contract once entries are published is hard, while subdividing the summary later is an addition that a reader treating `MayObserve` conservatively already withstands |
| D42 | **An ABI entry may carry a precondition, and a call violating one is outside every guarantee.** `Σ ⊨ G` condition (3) is quantified over the calls that respect it, the four properties carry a premise that the term does, and an implementation is neither obliged to detect a violation nor forbidden from doing so ([Semantics](../03-Typed-Core/06-Semantics.md)). `stella-base-0.1` has one such entry: reading a slot `Base.Array.unsafeNew` left unwritten ([Prim and Base](../06-Modules/02-Prim-and-Base.md)) | The alternative is to fault, and what that costs is not a line of specification but an initialization bit on every array and a check on every read — on the one operation a portable array library is built out of, and on a hot path no optimizer can generally clear. Leaving the count negative undefined would have been the same trade and is **not** taken: a backend has to do something deliberate with a negative length anyway, the check is once per allocation, and hosts genuinely diverge there, so that case faults. What makes the precondition tolerable is that it is discharged one layer up rather than by every author: `Data.Array` hands back no array with a slot unwritten, so an application reaching `unsafeIndex` through it respects the precondition without knowing there is one. **A precondition is not an observational effect and neither implies the other** (D41): `unsafeSet` carries no precondition and is observational all the same, while `unsafeIndex` on an unwritten slot is a violation whether or not anything would have moved the call. Keeping the notion explicit is what stops "undefined" from being read as "unspecified but safe": the violating program is outside type safety, which is stated rather than left to be inferred | Medium, and asymmetrically so. **Removing a precondition widens the specified domain**: every call that was already specified keeps its meaning, so it is source-compatible, but a backend that had been free to do anything on the previously unspecified inputs must now implement a meaning for them — so it may break a backend while breaking no program. **Adding one narrows the domain** and does the opposite: no backend has more to implement, and every caller relying on the input that has just become unspecified is broken |
| D43 | **The interpreter assembles its own foreign table, from a manifest.** A compiler emits one file per program naming, for each module, what the target reaches its implementations through; the interpreter reads it and builds the table, complete for a module before that module is loaded — a run reaching everything before the first load, a session reaching a module's implementations as that module arrives ([Foreign Manifest](../05-Backend/04-Foreign-Manifest.md), [Abstract Machine](../07-Runtime/01-Abstract-Machine.md)). **This withdraws the earlier decision that registering foreigns is not the interpreter's work** and that a complete table is handed to it. The mapping is written rather than inferred from a convention, the compiler builds the part this format fixes — the module and, from the declared types, the marshalling signatures (D44) — and passes the target's own part through unread, and an entry the ABI manifest fixes appears in no foreign manifest | The withdrawn design is not merely inconvenient, it does not reach: a table holds **host functions**, which no argument vector and no framing built for names and bytes can carry, so whoever assembles one must be in the process that uses it. That works while an application can link the interpreter and call it, and fails for the compile-time session — the compiler cannot link the interpreter without a cycle, so the session is a process, and a process cannot be handed host functions. One mode had to assemble its own table, and a rule holding for one mode and not the other would be two designs wearing one name. **A convention is rejected for a reason of the same kind**: taking the implementations of a module to be a file beside its source fits a backend whose implementations are source files and excludes one whose are not — a native target reaching a Rust crate cannot put it in a Stella tree — so the location is a fact about the build, and inferring it would make adding the second backend a change to the format. What keeps the format open is the split in what the compiler reads: it builds the part this format fixes — the module, the foreign names, and the signatures, all target-independent — and passes the target's own part through without interpreting it. Excluding the ABI-manifest names follows from the precedence rule rather than from a privilege granted to `Base`: such an entry is selected by name whatever a manifest said, so an entry for one would be written and never read | Medium. The file is a new compiler output and a new interpreter input, so changing it is a change to both; what it replaces was an interface between two libraries in one process, which was cheaper to change and could not be made to work |
| D44 | **A `foreign` declaration ranges only over types that can cross the boundary**, and the manifest carries, per foreign, how each argument and the result crosses ([Foreign Manifest](../05-Backend/04-Foreign-Manifest.md)). The kinds are the scalars, `Unit`, an `intrinsic opaque`, and a result of type `IO τ`; a data type, a record, a variant, a function, or a continuation is refused where the declaration is written. The signature is derived from the declared type by the compiler, which is the only party that has one | An implementation should be written against the host's own types and installed as it stands, and that is only true if something marshals — the interpreter holds every value in a shape of its own, and even a scalar is not the host's number until the boundary makes it one. **Marshalling cannot be inferred at the boundary**: a host number is one representation and two Stella values (D37), so `Int` and `Number` are indistinguishable there, and a `.dmo` carries no type to settle it. The signature therefore travels, and it travels in the manifest because that is the file the runtime already reads. **What cannot be marshalled is refused rather than passed raw**: a data value crossing as whatever the interpreter happens to hold would fix that representation for every backend and publish what is explicitly not a published ABI. The discipline this asks of an author is the one any backend boundary asks — expose the transparent value, bridge the abstract one above it in Stella — and refusing at the declaration is what makes it a compile error rather than a puzzle at run time | Medium. Widening the kinds later is compatible, a manifest naming a kind a reader does not know being rejected by the version rule; narrowing them is a breaking change to every declaration that used one |
| D26 | **`Base.*` is the versioned runtime contract, and what a backend owes is graded by profile.** It holds ABI entries, which a backend implements where a profile designates them, and protocols — standard primitive capabilities declared as effects, which have no implementation to supply and are interpreted by ordinary Stella code. `Prim` holds what the rules of Core name, `Base.*` the runtime contract, `Prelude` the default portable environment, and portable libraries are written in Stella over those. **Neither Core nor the ABI privileges a portable library**, whoever distributes it. `Base` is a prefix only the package implementing the ABI may claim, which package resolution verifies rather than the Core type checker, nothing in a Core module telling the ABI implementation of `Base.Int` from a forgery. The versioned ABI manifest defines the surface and the profiles over it, a backend manifest records which ABI entries one backend implements, and target validation is where the two are compared. `Σ` records the declarations themselves — a foreign scheme for an ABI entry, an effect declaration for a protocol — and records neither profile membership nor what a backend implements | To the type checker neither category is special: an ABI entry is an ordinary `foreign` and a protocol an ordinary `effect`, and each declared type is the same fact whichever backend compiles it, so `Σ` records both declarations and adds neither profile membership nor implementation coverage. A profile says what a backend is conformant *at*, which is more than the split between an entry whose absence leaves it unable to provide the standard runtime and one whose absence merely stops a program running. Naming the layer is also what makes the dependency legible: by D22 a module touching the ABI surface says so in its header, so portable code is distinguishable from code that is not. Fixing the direction of dependency is what the layering buys beyond a naming convention: `Prelude` owns the identity of the foundational types, so nothing it provides needs a library downstream of it | Medium. The layer is a naming and build-time discipline rather than a rule of Core, but where the boundary falls shapes the standard library |
| D37 | **`Int` is a 32-bit signed integer and `Number` is IEEE 754 binary64.** Together with D27's `Char`, a Unicode scalar value, every literal domain is fixed. **Literal identity is equality of the value**, which for a `Number` is equality of its bit pattern with all NaNs taken as one: `0.0` and `-0.0` are different literals | A domain two backends could disagree on would give one Core term two meanings, which is what the backend independence of Mid IR exists to prevent, so a domain belongs to Core rather than to a target or to the ABI. Both are what every target holds exactly: binary64 is what a JavaScript backend has natively and what Wasm's `f64` is, and 32 bits is Wasm's `i32` and what a JavaScript backend's bitwise operations give. `switchLit` requires its literals to be distinct, and IEEE equality decides nothing usable — it identifies the two zeros and separates a NaN from itself — so identity is on the bit pattern and a backend's dispatch implements that rather than `==`. What remains open is not a domain: which surface token denotes which value is the lexer's. Whether arithmetic wraps or faults on overflow is the ABI's to fix, and `stella-base-0.1` fixes it as wrapping ([Prim and Base](../06-Modules/02-Prim-and-Base.md)) | Low. A wider `Int` or a second numeric domain changes what a program computes, and a `.dmo` carries the width ([Encoding](../05-Backend/02-Encoding.md)) |
| D27 | **`String` is a sequence of Unicode scalar values and `Char` is one of them.** Every `Base.String` entry presents that meaning whatever a backend holds in memory, and a Stella `String` holds no unpaired surrogate. Operations counting UTF-16 code units or UTF-8 bytes live in the namespace of the target that has them — `Js.String`, `Wasm.String` — rather than in `Base.*` | Representation and meaning are separate concerns: a JavaScript backend may hold a JavaScript string and a Wasm backend UTF-8 bytes, and neither choice may reach a result. Were the meaning instead the target's own code unit, `length "😀"` would be 2 on JavaScript and 1 or 4 elsewhere — a difference in what a program computes rather than in how it is stored, reaching `switchLit`, equality, and every decomposition into `Char`. The cost falls where representation and meaning diverge, in how a JavaScript backend implements the string entries, and confining target-specific observation to a namespace the header names keeps that cost out of portable code | Low. It fixes what every backend presents and what the standard library may assume |

## Elaboration

| # | Decision | Rationale | Reversibility |
| --- | --- | --- | --- |
| D39 | **Elaboration is two layers: policy is guest Stella code and mechanism is the compiler's.** A synthesizer is an ordinary global, and `Synth ?m τ f` carries `f` as a resolved qualified name — a `SynthRef` — rather than a host function; it runs on Steam in a compile-time session whose host is the compiler. `Ψ`, the metavariables of types and of terms, unification, scope checking, the transaction, the queues, and fuel are the host's, and `Elab` is the boundary ([Elaborator API](../02-Surface-Language/03-Elaborator-API.md)) | Replaceable resolution policy is one of the properties the design claims, and a policy living in the compiler is replaceable only by editing the compiler. What must stay with the host is the solver's state: a rollback has to be exact, and a guest holding a copy of `Ψ` would give one question two answers. The split also fixes what a host synthesizer is for — a reference implementation for testing the scheduler and for the bootstrap, and **not** the provisional standard resolver, since writing that resolver in the host postpones the evidence for library-defined type classes indefinitely. The circle a guest synthesizer appears to close is cut by layering rather than by an exception: a kernel elaborator using no class, no macro, and no synthesis compiles the library the rest runs on | Medium. The boundary reaches the compile-time session protocol and what a synthesizer may assume, and no rule of Core |
| D40 | **A goal attempt is a transaction over the host's mechanism state, and `postpone` restarts it rather than resuming it.** An attempt commits or leaves nothing behind: the assignments and metavariables it made, the constraints it emitted, the terms it constructed, its changes to the queues, its warnings, and the fresh names it took are all restored, while fuel and the other resource counters are not. The generation counter a handle is stamped from is not restored either, and is kept apart from the supply of fresh names, which is. A guest synthesizer's heap is not the host's to restore, so what the guest owes in return is **observational restartability**: run against the same job and the same observable host state, it issues the same requests and reaches the same outcome, `Ψ` and the counters being inputs rather than hidden state. A `postpone`'s dependency set is admitted against the rolled-back `Ψ`; `transact` catches a diagnostic and not a postponement; and the blocked table registers a `PendingId` and holds no continuation, `assign` recording into the attempt's `Ψ` and enqueueing while the scheduler loop is the only thing that runs a job | Re-running is what the scheduler is specified to do, and what it costs without the transaction is a goal that duplicates its metavariables and its constraints once per attempt. The two halves of the rollback answer different questions: what is restored is what would otherwise accumulate across attempts, and what is not is what must not be undone — the loop has no decreasing measure to rest on, refining two flexible tails introducing a fresh metavariable, and a generation handed back would validate a stale handle against an object it never named. Admission is what the rollback then obliges: a metavariable the attempt created is gone, so a job registered under one waits on an assignment nothing can make. Distinguishing the two things `transact` might catch is the same split read inside one attempt — `Failed` says the candidate is not the one and `Stuck` says nothing about the candidate at all, so catching both would have a resolver discard a candidate a later assignment would have accepted. Saving a continuation instead would oblige a compile-time session to hold a suspended guest computation **between attempts**, a second continuation mechanism beside the one Steam has, and would leave a blocked entry a machine state where a description of work can be compared, counted, and reported on. Separating `assign` from execution is what keeps an attempt from opening inside another and a job from starting twice | Medium. Resuming rather than restarting is a change to the scheduler and to the session protocol; a synthesizer written against this contract is a function of its job and of what the host shows it, and stays correct under either |

## Mid IR and backends

| # | Decision | Rationale | Reversibility |
| --- | --- | --- | --- |
| D30 | **Mid IR is an A-normal form whose application spines are folded**, and a call whose callee and arity are both known statically is a **different construct** from one whose are not: `callk`, `ffi`, and `ctor` against `callu`, with `pap` for what is applied below its arity ([Mid IR](../04-MiddleEnd/01-Mid-IR.md)) | Core applies one argument at a time, and currying inserts an `openEff` per argument consumed under a non-empty ambient row (D8), so a saturated call to a pure global arrives as a chain wrapped several times over. **Folding is sound because of D35 and not otherwise**: with the argument evaluated before the function, a spine's arguments all reach values before any application happens, so collecting them into one call moves no effect. What the known/unknown split buys is that a known call is a transfer to an entry point whose arity is settled, needing no arity test and no under- or over-application to resolve, where `callu` needs all three. `pap` has to exist either way, Core requiring that a partially applied constructor be a value, so the split adds no machinery that avoiding it would save | Medium. It reaches the instruction set and every backend's calling convention, but no rule of Core. It moves with D35 |
| D31 | **A representation type is descriptive, not prescriptive.** Every Mid IR binding carries a `Rep` saying which class of value flows through it, and **no construct converts between representation types**; `Val` means unknown and is sound wherever a type is not to hand | Deciding boxing in Mid IR would be a representation decision, which is the one thing this stage exists not to make: a backend keeping one uniform representation ignores `Rep` entirely, and one choosing a Wasm GC struct per data type reads it and inserts the conversions its own choice calls for. Making `Rep` prescriptive instead would oblige translation to insert coercions for a representation no backend had yet chosen. The precision of a `Rep` is a function of what the Core term's annotation carries, and imprecision costs performance rather than correctness | Medium. Sharpening `Rep` is additive; making it prescriptive is not |
| D32 | **A `.dmo` keeps the structure a backend would otherwise rebuild.** A transfer to a join point names its destination and is never an offset, and a decision tree nests as a tree, each branch holding its own instruction sequence ([Bytecode](../05-Backend/01-Bytecode.md)) | Offsets into a flat array discard the loop and branch structure that a language with `if`, `switch`, and nested blocks needs, and recovering it means running a relooper — substantial to write, and what it recovers is worse than what was discarded. A consumer handed this form walks it instead, a nested dispatch becoming a nested `switch` and a join point a label or a local function. The cost falls on an interpreter, which resolves names and walks a tree rather than incrementing a program counter, and an interpreter is the one consumer for which a relooper could not be written at all | Low. It is the format, and every consumer of it |
| D33 | **The virtual machine provides genuinely multi-shot continuations.** Nothing in Mid IR or in the bytecode bounds how often one may be applied, and the machine that executes a `.dmo` is therefore **conforming with respect to D18** where the v0.1 JavaScript and Wasm backends are not. *How* it provides them — copying a captured segment at each application, sharing immutable frames, or anything else with the same meaning — is an implementation matter left to [Bytecode](../05-Backend/01-Bytecode.md) | Mid IR is designed before effect lowering is written, so a representation admitting one resumption would settle D18 by accident, in a stage with no standing to settle it. What conformance buys beyond itself is an evaluator that runs the programs the web backends cannot, which one carrying the same gap would not be. The cost falls on `full` clauses alone, a `fast` clause capturing nothing (D28). Fixing the mechanism here instead would rule out representations that mean the same thing | Medium. The Core decision is D18's; this is what one consumer undertakes about it |
| D34 | **The compiler's intermediate artefacts are `.dmi` and `.dmo`, and `.dmo` is what a backend outside this compiler builds on.** Mid IR is an in-memory representation; the interface file carries a module's exported types and what a downstream module needs in order to optimize | A consumer of Typed Core would have to perform erasure, A-normal form, spine folding, closure conversion, and the resolution of overlapping patterns before generating any code, and each is a place to differ from the reference compiler. Publishing the lowered form instead hands all of it over already done. The trade is that Core's types, rows, and effect rows are gone and `Rep` is what survives them, so optimization on the strength of a row belongs before this stage rather than after it. The JavaScript backend reads a `.dmo` as well (D45); the Wasm backend's input is fixed when that backend is designed | Medium, and low once anything outside this compiler consumes one |
| D38 | **Steam is a bytecode interpreter running on Node, and its core is independent of that host.** The interpreter is handed a decoded and validated `.dmo`, holds every value one way — `Rep` playing no part — and leaves memory to the host's collector. Its core — the stack, dispatch, continuations, handlers, regions, and loading — is written once, and a **foreign implementation is a host callable** behind one registry, an ES module export resolved by dynamic import on this host and a JavaScript adapter where the implementation is Wasm. It performs no just-in-time compilation, keeps no collector of its own, and allocates no registers. **It resolves no Stella module**: it runs as a session, given one module at a time and asked for the value a declaration holds, or as a run, given every module of a program in dependency order and asked to execute `main`; the order and the search for a `.dmo` are the front end's. The one thing it does reach for is a **host** module, and only where a manifest names it (D43). **Its delivered uses are the REPL and the compiler's own elaboration**: a synthesizer is guest Stella, which the compiler runs on this interpreter (D39). What that use adds is a protocol at the host boundary — applying a guest function to a goal the host holds, answering the `Elab` operations it performs, and discarding a run the host abandons — and whether that is a third mode or a capability of a session is open ([Abstract Machine](../07-Runtime/01-Abstract-Machine.md)) | Four uses want the same interpreter: the REPL, which is what reaches users; the compiler, which runs a synthesizer as guest code during elaboration (D39); a second evaluator to run a program against the Core evaluator; and running what D18 records the v0.1 backends as unable to run, a continuation applied more than once (D33). **What the compiler's use adds falls at the host and session boundary and nowhere else** — a guest function applied to an opaque handle, requests answered, a run abandoned — and not in the bytecode, the value representation, a collector, or a compiler of any kind inside Steam. The mechanism the guest asks of is the host compiler's and stays there (D39). A JavaScript host is what makes all of them cheap — Node is where the compiler already runs, and a JavaScript foreign is callable as it stands — while an interpreter compiled to Wasm would need bridges for strings, closures, continuations, and the JavaScript FFI before running anything, and would buy the REPL nothing. What must not follow from the host is the meaning of an instruction, which is Core's and the ABI's, so the boundary is drawn before there is a second host to discover it. A production machine of the kind the JVM and BEAM are is not the objective, and were one ever wanted it would come after the JavaScript and Wasm backends rather than before them | High for the host, which is a boundary crossed by design. Medium for the rest: no absence here reaches the bytecode, and an interpreter that later compiles or collects executes the same `.dmo` |
| D45 | **The JavaScript backend lowers from a `.dmo`, not from Mid IR.** It reads the module a decoder returns — a build that has just lowered may hand that value across without the bytes — and reaches nothing of Mid IR or Typed Core beside it. What it finds missing is added to the format rather than fetched from the side, and before the first released version of Stella the format changes freely for that reason ([JavaScript](../05-Backend/05-JavaScript.md)) | A first-class backend reading the published form is what shows D34's claim — that a `.dmo` is enough to build a backend on — before a release makes the format expensive to change; a backend reading Mid IR would leave the claim untested until a third party ran into its gaps. Every lower backend then derives from one artefact per module, so the machine and the JavaScript backend execute the same lowered program, and code is generated again without rerunning the front end. The route does not reduce the number of artefacts, Mid IR being written out on neither route, and it costs two things. The output is shaped by a register machine, which optimization over the backend's own representation recovers where it matters and which readability does not require. And a differential test between the machine and the backend cannot see a defect of lowering, both reading what lowering produced, so lowering is tested on its own and against an evaluator of Typed Core. What the file lacks — Core's types and effect rows above all — an optimization needing it runs before lowering for, or has recorded in the format | Medium. Reading Mid IR instead changes the backend's input and none of its runtime; what is costly to undo is whatever the format grew to serve it |
